# PengyOS — SPEC

> What PengyOS is built from, and why each piece was chosen over its alternatives.
> [`README.md`](./README.md) is the *why*; [`USE-CASES.md`](./USE-CASES.md) is *for
> whom* and wins when the two disagree. This file describes the system **as it ships
> in 26.10**; where a decision is still open or a piece is parked, it says so.

**Status legend:** 🟢 shipped / decided · 🔵 planned (strong default) · 🟡 open ·
⚪ parked

**Target hardware:** modern x86_64 with UEFI, N100-class mini-PCs and up, ~8 GB RAM.
Verified on Intel N100, Intel Alder Lake and Kaby Lake laptops, and an AMD Ryzen
6800H laptop; NVIDIA RTX via the opt-in NVIDIA edition. ARM is not a target yet.

**Editions:** one base, three additive layers. **Core ⊆ Server ⊆ Desktop**, plus an
opt-in **Desktop NVIDIA**.

```
        ┌──────────────────────────────────────────────┐
        │  DESKTOP   = Server + COSMIC + curated apps   │   (+ an NVIDIA image)
        ├──────────────────────────────────────────────┤
        │  SERVER    = Core  + remote-work + services   │   headless, comfortable
        ├──────────────────────────────────────────────┤
        │  CORE      = the shared, minimal, bootable base│
        └──────────────────────────────────────────────┘
             (one build engine, one verification layer)
```

Core is not a cut-down subset — it is the *exact* base the others are defined on.

> **Additivity rule.** A Desktop component never contradicts a Core decision; it only
> *adds*. If Desktop needs something different (a different init or libc), Core is
> wrong — fix it in Core, don't fork the stack. In the tree this is literal: each
> edition's defconfig is generated by stacking layer files
> (`buildroot-external/configs/layers/{core,server,desktop,nvidia}.config`).

## 0. Build engine — Buildroot 🟢

PengyOS is built from source with **Buildroot 2026.08**. Our recipes, board glue and
layers live in one `BR2_EXTERNAL` tree (`buildroot-external/`); upstream sources are
pinned tarballs plus our patches, so the system is assembled, never derived.

| Option | Why not (or why) |
|---|---|
| **Buildroot** 🟢 | One from-source engine that scales from a console box to a desktop; editions are config layers; we own every recipe we add; fastest to first boot. Weaker SBOM/reproducibility than Yocto out of the box, so we add those (§3). |
| Yocto / OpenEmbedded | Strongest reproducibility, SBOM and layering, but heavy and slow to iterate. Revisit only if Buildroot's limits bite. |
| LFS / BLFS | The spirit we want (a book of recipes we own), but an imperative cookbook with no dependency or update story. Buildroot gives us the same ownership with automation. |
| melange + apko | Bitwise-reproducible and SBOM-native, but container-image shaped. |
| Nix / Guix | Excellent ideas (content addressing, rollback) we borrow. Adopting Nix pulls nixpkgs in as the path of least resistance, and then we are derived from NixOS by the back door. |
| mkosi | An image builder only; it needs a package source underneath. |
| Debian / Arch / RHEL tooling | Excluded by principle: assemble, don't derive. |

**Known exception — COSMIC is host-built for now.** The COSMIC compositor, shell and
apps, `pop-launcher` and our two libcosmic apps are built with cargo on the build host
and copied in by `board/desktop/post-build.sh`, together with a few host libraries
they link (§7). This is the largest gap between "from source" and what ships; the
planned fix is Buildroot recipes for COSMIC (`tools/pengyos-cosmic-*`). Flatpak
itself is built from source (`package/flatpak`, with `appstream` and `libfyaml`).

## 1.5 Change model — immutable base, mutable surface

"Immutable or self-modifying?" is a false choice once two things are separated:

- **Where the system's *definition* lives** → declarative, versioned, reproducible
  (this repository).
- **How a change is *applied and undone*** → atomic and revertible.

Image-based immutability (OSTree, bootc, SteamOS) fuses the two because it serves
large fleets of identical machines run by untrusted operators. PengyOS machines are
few, all different, and maintained with an agent that can snapshot, diff, revert and
record what it did — so it keeps both, in layers:

| Tier | Surface | Who changes it | Mechanism |
|---|---|---|---|
| **0 — Base** | Kernel, libraries, the image itself | Nobody at runtime | A signed image written to the other A/B slot; boots once on trial, kept only if it reaches `multi-user.target` 🟢 |
| **1 — Machine** | `/etc`, services, driver config, users' data | The admin or Pengy | Lives on `data` (`/etc` is an overlay over the image's); never touched by updates 🟢. Snapshots and a change journal: 🔵 |
| **2 — Critical** | Signing keys, the update trust root, privilege changes | **A human signs** | Small, enumerated list 🟢 |

**Live fixes converge back into the definition.** A fix applied on one machine is
captured in the repo (a board fragment, an overlay file, a hardware profile), so the
next image already has it and the same surgery is never needed twice. Mutability
generates declarative knowledge.

## 1.6 Version policy — latest stable, pinned

Track the latest **stable** release of every component, not LTS lines, and pin it
exactly. The maintenance loop exists to keep up.

- **Engine:** Buildroot's current release line (2026.08).
- **Components:** the newest stable upstream release, pinned by version and hash.
- **Kernel:** latest stable, pinned (7.2.11 today); adopt a new mainline line within
  one or two releases of its `.0`, take point releases continuously.
- **The cost:** a non-LTS kernel gets only months of point releases, so we own the
  rebase cadence. `tools/pengyos-upstream-watch` and `pengyos-update-triage` exist to
  propose every move for human approval.

## 2. Editions

### 2.1 Core — the base

Boots a modern x86_64 machine to a networked, SSH-managed console.

- **Boot:** GRUB 2 EFI → kernel 7.2.11 → systemd. Video console (simpledrm/fbcon) and
  serial console; the GRUB menu is full-screen.
- **Userspace:** systemd (journald, udevd, logind, networkd, resolved), D-Bus, uutils
  coreutils (Rust), util-linux, kmod, iproute2, procps-ng, bash, Python 3, nftables,
  chrony, OpenSSH (key-only). The text/search tools come from the projects that define
  the behaviour, not from BusyBox: findutils, grep, sed, gawk, GNU time, which,
  diffutils, patch, gzip, Info-ZIP unzip, tar, tree, lsof, less, attr, psmisc — and the
  BusyBox applets for all of them are compiled out (`board/core/busybox.fragment`).
  `/bin/sh` is bash.
- **Storage tools:** e2fsprogs, btrfs-progs, dosfstools, exfatprogs, parted, LVM2,
  cryptsetup, efibootmgr.
- **Hardware:** a broad firmware set (Intel/Realtek/MediaTek/Qualcomm/Broadcom
  Wi-Fi, i915, amdgpu) and kernel drivers for the fleet's NICs, storage, sensors;
  Intel and AMD CPU microcode built into the kernel (applied by the early loader, no
  initramfs); the Intel IOMMU on by default; WireGuard.
- **Provenance:** `/etc/os-release` carries `IMAGE_ID`, `IMAGE_VERSION` and
  `BUILD_ID` (the git commit); the SBOM is embedded.
- **Image:** a disk image (`pengyos-core-x86_64.img`) written straight to the target.
  Core has no installer and no A/B layout yet, so it cannot update in place.

**Not in Core:** editors, containers, monitoring, any GUI or desktop library.

### 2.4 NVIDIA editions — opt-in

NVIDIA's proprietary driver on the **open kernel modules** (`package/nvidia-open`,
Turing / RTX 20 and newer) ships in two separate images, so the blob never reaches the
default ones; `pengyos-desktop-nvidia lint` enforces that.

| Image | Layers | Adds |
|---|---|---|
| **Server NVIDIA** (`IMAGE_ID=pengyos-server-nvidia`) | core + server + `nvidia-compute` | the driver's compute half: kernel modules, GSP firmware, CUDA driver API, NVML (`nvidia-smi`), NVENC/NVDEC, MPS, `nvidia-persistenced` (started when the module loads), and `nvidia-container-toolkit`'s CDI half, so podman shares the GPUs (`--device nvidia.com/gpu=all`). No GL. |
| **Desktop NVIDIA** (`IMAGE_ID=pengyos-desktop-nvidia`) | core + server + desktop + `nvidia-compute` + `nvidia` | the above, plus the EGL/GBM/Wayland and Vulkan/GL userspace and PRIME offload; no persistence daemon (it would keep a laptop's dGPU powered). |

The CUDA *toolkit* (nvcc) is not in either image: it lives in a container (the
`cuda` dev box, or an `nvidia/cuda` image under podman). A separate image rather than
a `systemd-sysext` extension (US-ALL-2): the extension machinery doesn't exist yet,
and an edition reuses the layers, the update feed and the installer as they are.

## 2.5 Supply & extension model — the four lanes 🟢

We cannot compile the world, and some of it (Steam) has no source at all. Unpacking
debs onto the host is the *least* reliable answer: their dependencies are Debian
package names, their binaries assume Debian's ABI and paths, and their maintainer
scripts assume dpkg — which ends in a partial Debian userspace on the host, derivation
by accident. So the OS extends through four lanes, ordered by trust:

| Lane | What | For | Trust posture |
|---|---|---|---|
| **1 — Recipes** | Buildroot recipes we own | everything with source | reproducible, SBOM, signed |
| **2 — Upstream artifacts** | a vendor's own prebuilt binary or tarball | tools that ship their own builds | pinned by hash; isolated prefix |
| **3 — Sandboxed apps** | **Flatpak** (primary), AppImage | third-party GUI apps, incl. proprietary | sandboxed (bubblewrap + portals); refs pinnable, mirrorable |
| **4 — Guests** | podman + **distrobox** | anything that needs a full distro userspace | isolated container, the vendor's own environment |

Per edition: Core = Lane 1; Server = 1, 2, 4; Desktop = all four, **Lane 3 is the
star**. Steam, Chrome, Discord and VS Code are Flatpaks; `tools/pengyos-debx`
(bounded deb/rpm extraction that never runs maintainer scripts) remains for the rare
Lane 2 case.

**Trust rule.** Installing a binary that runs with system access is a Tier-2 (human)
act; sandboxing is how untrusted binaries are accepted without being trusted.
Proprietary blobs are contained guests, never system components — with one carve-out:
**GPU drivers** are kernel modules and cannot be guests, so the only lever is which
image carries them. NVIDIA's ships only in the opt-in NVIDIA editions, which are
therefore not fully from source.

## 4. Install & update

**Shipped 🟢** (details in [`docs/state-layout.md`](docs/state-layout.md)): GPT with an
ESP, two read-only ext4 root slots and a btrfs `data` partition. GRUB picks the slot.
`pengyos-update apply` writes the new image into the other slot, runs the new image's
own `update.d` steps, and sets a one-shot `pengyos_try`; the new slot is kept only if it
reaches `multi-user.target`. Updates never touch `data`. Feeds match on `IMAGE_ID`.
Installers: `pengyos-install` (engine), a console wizard (Server) and a libcosmic GUI
(Desktop), all on the edition's USB stick.

**Parked ⚪** ([`docs/install-update-architecture.md`](docs/install-update-architecture.md)):
UKI + systemd-boot + boot counting + systemd-sysupdate + Secure Boot + TPM2. It was
designed in full, but the smaller GRUB "A/B lite" shipped first and covers the user
stories. Its UKI, boot-chain, boot-count and sysupdate tools were retired on
2026-10-03 (they are in git history); `pengyos-secureboot-*` stays. Secure Boot + TPM is the part
most likely to come back.

## 5. Rubric — two worked examples

See [`docs/principles.md` §Component selection rubric](docs/principles.md#component-selection-rubric).

**Coreutils.** uutils scores best (MIT, memory-safe, the Ubuntu default since 25.10)
and has shipped since 26.10.25: our own Buildroot recipe (`package/uutils-coreutils`,
pinned 0.11.0, `--no-default-features --features unix`), one multicall binary plus a
symlink per utility. GNU coreutils was the incumbent only because Buildroot had a
recipe and we did not. *Interfaces stay POSIX either way, so the swap was cheap.*

The swap surfaced the bigger userland finding: Buildroot resolves BusyBox overlaps by
**install order** (`BUSYBOX_DEPENDENCIES` lists coreutils, grep, tar, … so they build
after BusyBox and their files win), and an applet no package claims simply stays —
cut down. 144 applets were in the Server image, and the tools agents reach for were
among them: `find` without `-printf`, `grep` without `-P`/`--include`, `sed` without
`\b`, `awk` without `gensub`, `xargs` without `-d`, `diff` without `-r`, `time -v`,
`unzip -l`, `killall -q`, `losetup -f`, `last -x`, `su -l`. They read like the real
tools and behave like an initramfs — in an image with **no initramfs**. PengyOS now
resolves the overlap in the BusyBox config instead of by luck: every applet another
package owns is compiled out, the early-boot and embedded applets go with it, and
`scripts/tests/test_core_userland.py` fails if a fragment names a symbol BusyBox does
not declare (a typo is a silent no-op) or removes a command no selected package
provides.

**Init → systemd.** Freedom 🟡 (LGPL-2.1, fine) · maintenance ✅ · security 🟡 (large
but well audited) · dependencies 🔴 (it drags a lot, and forces glibc) · interface ✅
(the contract every other component expects) · replaceable 🟡. **Kept for the
contract, not loved** — "replace interiors, not interfaces".

## 6. Open decisions

1. **LSM:** turn on AppArmor (profiles exist) or choose SELinux. 🟡
2. **Secure Boot + TPM2:** bring back the signed chain on top of GRUB, or return to
   the UKI/systemd-boot design. 🟡
3. **COSMIC from source:** Buildroot recipes for COSMIC, so the Desktop no longer
   depends on the build host's userspace (§7). Flatpak is done. 🔵
4. **Core updates:** give Core the A/B layout and an installer, or keep it a
   write-once image. 🟡
5. **A self-hosted Flatpak remote** (mirror + our own apps). 🟡
6. **Firmware policy** where no free firmware exists — today: ship it, list it. 🟡
7. **ARM** (alongside x86_64). ⚪
8. **Name:** PengyOS vs a name distinct from the Pengy assistant. 🟡
9. **The replacement ladder:** how far down the stack we go, and on what cadence.
   **Answered 2026-10-06** — banded by *verifiability, not difficulty*: additive →
   fork upstream → replace a userland component → replace a contract-bearing
   subsystem (research track) → not on the list. Kernel, NVIDIA blobs, Wayland
   protocol and a browser stay non-goals, by verifiability rather than capability.
   Component replacement is supported from a `BR2_EXTERNAL` tree via Buildroot's
   virtual-package providers — the mechanism's own documentation replaces the init
   system. See [`docs/stack-down-replace.md`](docs/stack-down-replace.md). 🟢
10. **Divergence budget and fork policy:** what makes a maintained fork admissible,
    and how many we may carry. **Answered 2026-10-06** — at most **10** maintained
    forks (current: 0), each with a named expiry condition and its own observe
    source; creating a fork is a **Tier-2 human sign-off**, not a nightly action.
    Ledger: [`divergence.toml`](divergence.toml). 🟢
11. **Outward AI-assisted contribution posture:** attribution convention, and what
    we do when an upstream will not accept our authorship model. **Answered
    2026-10-06** — disclose using the host project's own convention (kernel-style

## 7. Build host, bootstrap & verification

### Build host

Any x86_64 Linux machine with KVM, ~16 GB RAM and ~150 GB of disk builds Core and
Server: Buildroot builds its own toolchain, and the host only supplies Buildroot's
prerequisites (`scripts/provision-build-host.sh`). The **Desktop** additionally takes
from the host:

- the COSMIC components and our libcosmic apps, built with cargo
  (`scripts/build-cosmic.sh`, pinned to the versions in
  `scripts/cosmic-components.tsv`, with the patches in
  `board/desktop/cosmic-patches/`);
- the shared libraries the host-built COSMIC Store, Player and App Library link
  that the image does not build (GStreamer bits, an OpenSSL/curl pair with
  ENGINE support), plus six libraries `cosmic-comp` needs.

So a Desktop build is only as reproducible as its host: the verified host is **Ubuntu
26.04**, and the provisioning script installs exactly the packages those copies come
from. Removing this dependency is open decision §6.3.

### Bootstrap chain

| Stage | Who builds what | Trust |
|---|---|---|
| **A (now)** | an Ubuntu host builds PengyOS | the host is the trusted seed — a documented gap |
| **B** | PengyOS Server builds PengyOS | first self-hosting step |
| **C** | PengyOS builds itself | bootstrap solved |

The route from A to B is reproducibility: when two hosts produce identical artifacts
from identical inputs, the seed no longer has to be trusted — it can be checked.
For Core and Server that check has been done (26.10.3: an Ubuntu 26.04 host and an
Ubuntu 26.04 distrobox on a PengyOS Desktop gave identical images).

### Verification

- **QEMU + KVM**, q35, **OVMF** (UEFI), optional **swtpm** (TPM2), headless on the
  serial console: `pengyos-qemu-verify boot` and `smoke` (Core and Server matrices,
  grounded in real boot logs). `docs/qemu-testing.md` covers SSH into a guest and
  screenshots of the Desktop.
- **Not testable in a VM:** GPU drivers (NVIDIA), suspend/resume, firmware, thermal,
  Wi-Fi/Bluetooth/printing hardware. These are checked on the fleet before a release.

### "Core is done" gate

Boots under OVMF+KVM to a login ✅ · passes the smoke matrix ✅ · emits an SBOM ✅ ·
updates are signed ✅ (Server/Desktop) · rebuilds reproducibly ✅ (two hosts, 26.10.3) · measured boot ⚪ ·
updates in place 🟡 (§6.4).

## [Unreleased]

### Added

- **Hardened the GitHub-ready contract test** (`tests/test_github_ready.py`).
  The `test_github_ready` suite now *parses* `pyproject.toml` with the stdlib
  `tomllib` instead of only substring-matching it, and asserts the parseable
  project metadata a packager needs (`name`, `version`, `description`,
  `readme`, `license`, `requires-python`). It also checks that the importable
  `__version__` matches the declared project version (catches install/repo
  drift), that `LICENSE` carries the *full* canonical MIT body (not just the
  words "MIT" + copyright), and that the `LICENSE` file and the pyproject
  `license` field agree. A README with an H1 heading and a non-trivial body is
  required. This closes a real gap: a malformed `pyproject.toml` or version
  drift previously slipped past the substring-only checks. (`pytest -q` = 248
  passed / 5 skipped.)
- **Grounded the round-trip in a committed signed fixture** (`tests/fixtures/`).
  - A real, checked-in signed ESP plus its PK/KEK/db trust root:
    `tests/fixtures/keys/` (PEM certs + `0600` private keys, the Ed25519
    verification-key sidecar, `signatures.json`) and
    `tests/fixtures/signed_esp/` (the pinned boot-chain binaries, each signed).
    Generated by `tests/fixtures/build_fixtures.py` (which drives the real
    library), so the fixtures are reproducible and auditable rather than
    hand-fabricated.
  - `tests/conftest.py`: the `signed_fixture` fixture (a writable temp *copy* of
    the committed tree, so tests may mutate it without dirtying the checked-in
    copy) and `foreign_key_set` (a second key set with a distinct `db` key id --
    the honest model of a signer not in `db`).
  - `tests/test_fixtures.py` (15 cases): a signed tree lints clean (via both
    `lint_esp` and the `lint` CLI); each mutation fires exactly its rule against
    a copy of the committed fixture -- `unsigned`, `untrusted_signer` (wrong
    key), `untrusted_signer` (db entry removed), `signature_invalid` (tampered
    bytes), `missing`; plus a determinism guard that rebuilds the fixture and
    asserts it matches the committed tree byte-for-byte.
- `pengyos_secureboot_enroll.truststate`: the trust-state data model.
  - The PK/KEK/db key set (`KEY_FILES`, `KEY_ROLES`) and its permission policy
    (`KeyPerms`: `0600` private / `0644` cert), mirroring the sibling
    `pengyos-sbkeys` package.
  - Key identification by the SHA-256 fingerprint of the DER certificate
    (`key_fingerprint`) -- the same identifier MOK/mokutil uses, and the reason
    `keys --rotate` changes a key's id.
  - `KeyEntry` (a key in the trust root, with `is_signing_key` = the `db` key)
    and `EspBinary`/`EspManifest` (the set of EFI binaries the ESP must ship,
    each optionally pinned to a signing key id). Paths are canonicalised in
    POSIX form with a `..`-traversal guard; `EspManifest` dedupes by path.
  - `load_expected_binaries` to build a manifest from ESP-relative paths.
- Test suite (`tests/test_truststate.py`, 30 cases) including an opt-in
  (`PENGYOS_IT=1`) check that the fingerprint scheme matches a real openssl
  certificate.
- `pengyos_secureboot_enroll.bootchain`: the pinned PengyOS ESP boot-chain
  layout -- the concrete set of EFI binaries the ESP ships, so `sign-chain`/`lint`
  build a real manifest.
  - `/EFI/systemd/systemd-bootx64.efi` (systemd-boot at its `bootctl install`
    path), the UEFI-spec mandatory fallback `/EFI/BOOT/BOOTX64.EFI`, and one UKI
    per installed version/slot under `/EFI/Linux/` (`EFI/Linux/pengyos-
    <edition>+<ver>-<slot>.efi`, the A/B boot state). Pinned from the PengyOS
    install & update architecture doc (pinned 2026-09-24) and the canonical
    systemd-boot install paths.
  - `expected_manifest(edition, version, slots)` assembles the manifest (systemd
    -boot, fallback, then one UKI per slot, deduped by path). Every entry pins
    `key_id = None` ("any db key") until the `keys` subtask pins the `db`
    fingerprint.
- Test suite (`tests/test_bootchain.py`, 21 cases) pinning the layout.
- `pengyos_secureboot_enroll.keys`: the `keys` subtask -- generate/rotate the
  PK/KEK/db trust root, load it from disk, and emit signed, hashable key
  metadata.
  - Deterministic generation into a fixture dir through an **injectable openssl
    shim** (`generate_private_key` / `generate_certificate` / `generate_all`);
    the default shim runs real `openssl` (EC P-256 keys, self-signed X.509
    certs), tests inject a deterministic stand-in so generation is reproducible
    and needs no external tool. Private keys get `0600`, certs `0644`, the key
    dir `0700`.
  - `load_key_set` reads each `<role>.cert` (PEM), derives the DER with the
    standard library (`pem_to_der`, no openssl), and computes the key id as the
    SHA-256 of that DER -- returning a `TrustRoot` of `KeyEntry` objects.
  - `KeyMetadata` (an immutable, hashable dataclass) carries the role/key-id
    table and a `digest` (SHA-256 of its canonical bytes); `build_metadata`
    produces it, `sign_metadata` signs the canonical bytes with the `PK` key,
    and `verify_metadata_signature` checks it against the `PK` cert. The signed
    metadata is self-verifying (`KeyMetadata.from_json` restores the canonical
    form from the on-disk JSON).
  - `pengyos_secureboot_enroll.cli:cmd_keys` wires it into the `keys`
    subcommand: generate (or `--rotate` to regenerate), load, sign + persist
    `metadata.json`/`metadata.sig`, and print a report (or `--json`). Never
    prints key material; refuses insecure-perm keys (fail closed).
- Test suite (`tests/test_keys.py`, 24 cases) covering generation, perms,
  DER/key-id loading, signed+hashable metadata, and the `keys` CLI, plus an
  opt-in (`PENGYOS_IT=1`) real-openssl generate->load->sign->verify round-trip.
- `pengyos_secureboot_enroll.sign_chain`: the `sign-chain` subtask -- sign each
  EFI binary on the ESP, record the signature binding (sha256 + db key id),
  verify, and persist the bindings for `lint`.
  - **Injectable signer** (`pengyos_secureboot_enroll.signer`): a stdlib
    Ed25519 implementation (default) and an openssl-CLI shim (real EC P-256
    ECDSA). `select_signer()` picks one; the openssl shim is injectable so tests
    never call real `openssl`.
  - **Pure-Python Ed25519** (`pengyos_secureboot_enroll.ed25519`, RFC 8032):
    signs a 32-byte seed (derived from the db private key) and verifies against
    the matching public key, which is written alongside the db cert as
    `<cert>.ed25519.pub` (public material) so verification needs no private key.
  - `sign_binaries(esp, manifest, trust_root, signer)` signs every binary in the
    manifest present in the ESP, verifies each, and raises `SignChainError`
    (fail closed) on any missing binary or failed verification. Emits the
    Ed25519 verification-key sidecar before verifying so the round-trip holds.
  - `SignatureBinding` (path, sha256, key_id, signature, signer) +
    `SignedChain` are JSON-serialisable; `save_bindings`/`load_bindings` persist
    them to `signatures.json` (0644) and `verify_bindings` re-checks each binding
    against the ESP bytes + db cert (used by `lint`).
  - `pengyos_secureboot_enroll.cli:cmd_sign_chain` wires it in: loads the trust
    root (refusing insecure-perm keys), builds the manifest from `--edition` /
    `--version` / `--slots` (defaulting to a single `a` slot), signs with
    `--signer stdlib|openssl`, and prints a report or `--json`. Never prints key
    material.
- Test suites (`tests/test_ed25519.py`, RFC 8032 vectors + negative cases;
  `tests/test_sign_chain.py`, ~30 cases) covering the signer, the round-trip,
  tamper/wrong-key/missing detection, bindings persistence, and the `sign-chain`
  CLI, plus an opt-in (`PENGYOS_IT=1`) real-openssl sign->verify round-trip.
- `pengyos_secureboot_enroll.enroll`: the `enroll` subtask -- emit the MOK /
  custom-key enrolment material + operator instructions (no NVRAM writes).
  - **DER db certificate** (`db_cert_der`): the `<dir>/DB.cert` (PEM) is
    DER-decoded with the standard library (`pem_to_der`) -- the exact bytes
    `openssl x509 -outform DER` emits and what `mokutil --import` consumes.
  - **`EnrolmentMaterial`** carries the `db` key id, the DER cert, and the
    PK-signed key metadata (the metadata digest + signature bind the material to
    the trust root). Two modes:
    - **`mok`** -- the artefact is the DER cert; the instructions walk the
      operator through `mokutil --import db.cert.der` and confirming the key in
      the rebooting MOK manager.
    - **`custom`** -- a self-authenticating `enrolment.json` bundle (base64 DER
      cert + key id + signed metadata) for a custom signing pipeline.
  - **`build_enrolment`** fails closed up front (`check_key_set`) on a missing
    cert or any private key with insecure permissions, then loads the trust root
    and signs the metadata with the PK key.
  - **`write_enrolment`** writes `db.cert.der` + `instructions.txt` (both modes)
    and, for `custom`, `enrolment.json` -- all world-readable (`0644`, public
    material). The private keys are never written out.
  - `pengyos_secureboot_enroll.cli:cmd_enroll` wires it in: loads the trust root
    (refusing insecure-perm keys), builds the material in `--mode mok|custom`,
    writes it to `--out` (default: cwd), and prints a report (or `--json`). Never
    prints key material; writes no firmware NVRAM.
- Test suite (`tests/test_enroll.py`, 22 cases) covering DER extraction, both
  modes, the JSON bundle round-trip, the instructions, the file layout (incl.
  "no private key written out"), the `enroll` CLI (report/JSON/missing-key/
  insecure-perm/default-out), plus an opt-in (`PENGYOS_IT=1`) real-openssl
  round-trip that checks the DER equals `openssl x509 -outform DER`.
- `pengyos_secureboot_enroll.lint`: the `lint` subtask -- assert that every
  expected EFI binary on the ESP is signed by a key present in `db`.
  - **Three rules**, each emitting a `LintViolation(path, reason)`:
    - `unsigned` -- a binary with no recorded signature binding (would be
      rejected by the firmware);
    - `untrusted_signer` -- a binding whose `key_id` is not one of the trust
      root's `db` key ids (a signer the firmware does not trust); and
    - `signature_invalid` -- the recorded signature does not verify over the
      current ESP bytes against the `db` certificate (a tampered / forged
      binary).
  - `lint_esp(esp, manifest, trust_root, bindings)` applies the rules in order
    per expected binary and returns a `LintResult`; `LintResult.verified` is
    `True` only when there are no violations and at least one binary was checked
    (an empty ESP is not a passing lint). The signature checked is the binding
    `sign-chain` wrote to `signatures.json` -- the on-disk artefact that stands
    in for the Authenticode signature the firmware reads from the binary. No
    root, no real NVRAM; verification runs through the injectable signer.
  - `pengyos_secureboot_enroll.cli:cmd_lint` wires it in: loads the trust root
    (refusing insecure-perm keys), builds the pinned boot-chain manifest, loads
    `signatures.json`, and reports the result (or `--json`). The ESP lints clean
    (exit 0) only when every expected binary is present, signed by `db`, and the
    signature verifies; any violation is reported on stderr and the command
    exits 1 (fail closed). Never prints key material.
  - Test suite (`tests/test_lint.py`, 25 cases + 1 opt-in integration) covering
    the clean tree, each mutation firing exactly one rule, the `LintResult`
    contract, and the `lint` CLI (clean/unsigned/wrong-key/tampered/JSON/
    missing-key/insecure-perm/no-key-material), plus an opt-in
    (`PENGYOS_IT=1`) real-openssl sign->verify->lint round-trip.

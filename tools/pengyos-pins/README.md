# pengyos-pins

Pinned component manifest for [PengyOS](../../README.md).

`pengyos-pins` is a single source of truth for pinned components. Each
component records its **version**, **upstream**, **url**, **sha256**,
**license**, and **edition-membership**. From that manifest the tool:

- **validates** `pins.toml` (required fields, SPDX license-id syntax, hash
  format),
- **emits** a Buildroot config fragment and a human/markdown/JSON report,
- **locks** a resolved snapshot of the manifest to `pins.lock.toml`, and
- **detects drift** between the working `pins.toml` and that lockfile.

## Usage

```console
$ pengyos-pins --help
usage: pengyos-pins [-h] [--version] COMMAND ...

Pinned component manifest for PengyOS: validate pins.toml, emit a Buildroot
fragment + report, and detect drift against a lockfile.

positional arguments:
  COMMAND
    version     print the pengyos-pins version and exit
    validate    validate a pins.toml file (required fields, SPDX, hash format)
    emit        emit a Buildroot config fragment or a report from pins.toml
    lock        write the resolved manifest to a lockfile (pins.lock.toml)
    drift       diff pins.toml against a lockfile (added/removed/version/hash)

Run `pengyos-pins COMMAND --help` for per-command options.
```

The full command surface (`validate`, `emit --format buildroot-fragment|report|json`,
`lock`, `drift --lock pins.lock.toml`) is added by successive implementation
tasks.

### validate

`pengyos-pins validate [PINS.TOML]` (defaulting to `pins.toml`) enforces the
whole manifest contract and exits non-zero on the first problem:

```console
$ pengyos-pins validate pins.toml
ok: 3 component(s) valid

$ pengyos-pins validate pins.toml
invalid: component[1]: license 'not a license' is not a valid SPDX expression ...
invalid: component[2]: sha256 'ABCDEF' is not a 64-character lowercase hex digest ...
```

Exit codes: `0` valid, `1` the file failed validation or could not be
read/parsed, `2` a usage error.

### emit

`pengyos-pins emit [PINS.TOML] --format {buildroot-fragment,report,json}`
(defaulting to `pins.toml`) turns a validated manifest into artefacts. It
validates first, then prints the chosen format to stdout:

```console
$ pengyos-pins emit pins.toml --format buildroot-fragment
# Generated by pengyos-pins — PengyOS Buildroot config fragment
# One 'CONFIG_<SYMBOL>=y' line per pinned component (name-sorted).

CONFIG_BUSYBOX=y
CONFIG_LINUX=y
```

The Buildroot fragment is one `CONFIG_<SYMBOL>=y` line per component, in
name-sorted order, with a Buildroot-safe symbol mapping (upper-case, dashes →
underscores, so `linux-libre` → `CONFIG_LINUX_LIBRE`). It is deterministic and
re-parseable. The `report` format is a Markdown human-readable summary; `json`
is a machine-readable document. Exit codes: `0` success, `1` the file failed
validation or could not be read/parsed, `2` a usage error.

### lock

`pengyos-pins lock [PINS.TOML] [--lock PATH]` writes a **resolved lockfile**
(default `pins.lock.toml`) from a validated manifest. The lockfile is a
committed snapshot of the resolved components (version + sha256, plus the full
component record) and is the baseline that `drift` compares against:

```console
$ pengyos-pins lock pins.toml
locked: 2 component(s) -> pins.lock.toml
```

Only a manifest that passes validation is locked (the lockfile is the resolved
baseline, so it must itself be a valid manifest). Exit codes: `0` success, `1`
the file failed validation / could not be read / could not be parsed, `2` a
usage error.

### drift

`pengyos-pins drift [PINS.TOML] [--lock PATH]` diffs the working manifest
(default `pins.toml`) against its lockfile (default `pins.lock.toml`) and reports
what changed:

```console
$ pengyos-pins drift pins.toml
drift detected between pins.toml and pins.lock.toml:

  added:      1
  removed:    1
  version:    1
  hash:       1

added:      musl (1.2.5)
removed:    gcc (14.0)
version:    linux 7.2.5 -> 7.3.0
hash:       busybox aaaaaaaa... -> bbbbbbbb...
```

`drift` reports **added** (in `pins.toml`, not the lockfile), **removed** (in the
lockfile, not `pins.toml`), **version-changed**, and **hash-changed** entries. A
component that changed both version and hash is reported once as a version
change. Exit codes: `0` no drift, `1` drift detected (or the pins/lock file
could not be read/parsed) — so it doubles as a CI guard against unreviewed
manifest changes. A missing lockfile is a hard error (run `lock` first).

## pins.toml schema

Components are declared as an array of tables:

```toml
[[component]]
name = "linux"                       # [a-z0-9][a-z0-9_-]*, unique
upstream = "https://linux.org"       # canonical upstream URL
version = "6.12"                     # upstream version string
url = "https://cdn.org/linux-6.12.tar.xz"
sha256 = "0123...abcd"               # 64 lowercase hex chars
license = "GPL-2.0-only"            # SPDX expression
edition-membership = "core"         # optional
```

The schema, validation rules, and emit/drift formats are documented in
[`spec.md`](spec.md).

## Development

Requires Python ≥ 3.11 (standard library only at runtime; `tomllib` is used
for `pins.toml`).

```sh
python3 -m pytest -q        # run the test suite
python3 -m pengyos_pins     # run the CLI without installing
```

To install the `pengyos-pins` entry point: `pip install .` (or `pipx`).

## Layout

```
pengyos_pins/   package (cli.py, schema.py, validate.py, emit.py, lockfile.py)
tests/          pytest suite (no network, no root; integration tests opt-in
                behind PENGYOS_IT=1)
```

`pengyos_pins.schema` defines the `pins.toml` data model: the frozen
`Component` dataclass (name, upstream, version, url, sha256, license, optional
edition), the immutable `Pins` container, and the pure, side-effect-free
`load_pins`/`parse_pins` loader that validates structure, required fields,
string typing, the `[a-z0-9][a-z0-9_-]*` name rule, and name uniqueness.
`pengyos_pins.validate` enforces the semantic rules the schema defers: SPDX
license-expression syntax and the sha256 hex format.
